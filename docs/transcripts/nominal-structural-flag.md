# Nominal‑Structural Flag in Polytropos

This note explains the role of the *nominal‑structural* phantom flag in the Polytropos design, how it interacts with the runtime representation, and why it is essential for preserving backward compatibility while providing extensible records and variants.

## Runtime representation (unchanged)

Polytropos builds on the `large‑records/large‑anon` approach:

```haskell
data Rep f a = Rep {-# UNPACK #-} !Word !(SmallArray (f Any))
```

- The `Word` stores the **hash** of the constructor/field name (obtained via `KnownHash`).
- The `SmallArray (f Any)` holds the payload fields in a fixed order determined by a per‑type hash‑→‑index map generated by the GHC plugin.

A wrapper distinguishes products vs sums:

```haskell
data RowRep f (rf :: RowType) (r :: Row k) a = RowRep (Rep f a)
```

- `rf :: RowType` is either `'ProductRowT` (record‑like) or `'SumRowT` (variant‑like).
- `r :: Row k` is the actual row (type‑level list of `(label := type)` pairs).
- The phantom `a` is usually `()` for the representation itself; concrete values instantiate `a` with the appropriate payload type.

**Importantly:** this layout contains **no** explicit nominal/structural or anonymous/named information. All such distinctions live solely in the type level.

## The nominal‑structural flag

To express whether a given row should be treated **nominally** (closed, named constructors) or **structurally** (open, row‑polymorphic), we add a second phantom parameter:

```haskell
data AnonymousFlag = Named | Anonymous   -- promoted to a kind via DataKinds

data RowRep f (rf :: RowType) (af :: AnonymousFlag) (r :: Row k) a =
    RowRep (Rep f a)
```

### Meaning of the flag

| `af`          | Interpretation                                            |
|---------------|-----------------------------------------------------------|
| `'Named`      | The row corresponds to the **declared** constructor set of a datatype (nominal, closed). |
| `'Anonymous`  | The row was constructed by an **anonymous** expression (`ANON { … }` or `VAR { … }`) and is therefore structurally extensible. |

### Why we need it

1. **Distinguishing user‑declared types from anonymous ones**  
   - A normal `data` declaration (e.g. `data Point = Point { x :: Int, y :: Bool }`) should be treated as nominal: its set of fields is fixed, and pattern matching should be exhaustive.  
   - An anonymous record `ANON { x = 3, y = True }` must be treated structurally: the type variable can be instantiated with any super‑row, and generic operations (`AllFields`, `SubRow`, etc.) should apply.

2. **Enabling backward compatibility**  
   - By **default**, ordinary `data`/`newtype`/`type` declarations set the flag to `'Named`.  
   - Extensibility is only activated when the user explicitly opts‑in (via a pragma such as `{-# LANGUAGE ExtensibleRecords #-}` or a dedicated keyword like `data open … where …`).  
   - Existing code that does not enable the extension sees exactly the same nominal semantics as before, preserving exhaustiveness guarantees, instance coherence, and module abstraction.

3. **Guiding the plugin’s constraint solving**  
   - The GHC type‑checker plugin uses the flag to decide which solvers to activate:  
     - When `af = 'Named`, the plugin may still generate `KnownHash` evidence but typically **does not** produce `AllFields`, `SubRow`, etc., unless the user asks for them separately.  
     - When `af = 'Anonymous`, the plugin fully activates the row‑polymorphic machinery: `KnownHash` for each label, `AllFields`/`AllCons` for generic traversal, `SubRow`/`SubVar` for projection/injection, and the source‑plugin can desugar `ANON { … }` / `VAR { … }` into calls to the runtime constructors.

### Example usage

```haskell
-- Anonymous record (structural)
let p = ANON { x = 3, y = True }
-- Desugars to something like:
-- RowRep (Rep (hashVal @"x") (fromList [I# 3, B# True]))
--   :: RowRep f 'ProductRowT 'Anonymous '["x" := Int, "y" := Bool] ()

-- Nominal record (closed, user‑declared)
data Point = Point { x :: Int, y :: Bool }
-- If we want Point to be definitionally equal to the anonymous type:
type family PointRep where
  PointRep = '["x" := Int, "y" := Bool]
type Point = RowRep f 'ProductRowT 'Named PointRep ()
-- The underlying `Rep` is identical; only the phantom flag differs.
```

### Interaction with other phantoms

- `rf :: RowType` still distinguishes **product** (`'ProductRowT`) from **sum** (`'SumRowT`).  
- Combined with `af`, we have four meaningful combinations:
  1. `'ProductRowT`, `'Named`  → nominal record (closed product).
  2. `'ProductRowT`, `'Anonymous` → anonymous record (`ANON { … }`).
  3. `'SumRowT`, `'Named`   → nominal variant (closed sum).
  4. `'SumRowT`, `'Anonymous`   → anonymous variant (`VAR { … }`).

All four share the same runtime layout (`Rep`), differing only in the erased phantom parameters.

## Key claim under review

What this transcript currently describes is a **type‑level marker** (`Named` vs `Anonymous`) on `RowRep`. That is **not** the same thing as a closed/open row discipline in the type system — it is more like a policy label that tells the plugin how to interpret a row.

## What ‘open vs closed’ changes, and what it does not

If the intent is “closed‑for‑declared‑types, open‑for‑structural‑extension”, the stronger conceptual axis is really **closed vs open rows**, not nominal vs structural. That said, importing the concept of open vs closed rows is necessary but not sufficient:

- A pure phantom `IsClosed`/`IsOpen` (or `Named`/`Anonymous`) changes the *label* on the type, but it does not by itself give the operational semantics of open rows.
- To function as real open rows you would also need at least: a row‑tail/row‑variable representation at the type level; unification/instantiation rules for that tail; a row‑inclusion/subrow relation and its treatment; row polymorphism in generalisation/instantiation; and a closedness‑aware match/elimination story.

So the current `Named`/`Anonymous` flag should be read as a **first cut at a closed‑by‑default discipline**, not as a full closed/open row algebra.

## Honest scope note

There is a real fork in intent behind the nominal‑structural question:

1. **Library‑level open records/variants with known‑row evidence.** Polytropos can plausibly do useful work here without a full row‑kind/unification story. This is compatible with the current plugin/evidence‑class trajectory.
2. **Real row polymorphism with open rows.** This is a larger type‑system change and is a different kind of project from the current literal‑index plugin.

The `Named`/`Anonymous` flag is most naturally read as an attempt to serve (1) with a clearer closed‑default framing. It is not, by itself, (2).

## What remains to be reconciled

- The shipped `RowRep` vocabulary has no row tail/variable and no open‑row representation; the `row` parameter is fully known at the use site.
- The test suite specifies against fully known rows only; there is no test exercising genuine open‑row behaviour beyond knowing the row at the use site.
- The design note’s plugin obligations are still framed around literal index/tag/body solving over known rows.

So the nominal‑structural flag is a reasonable **story device** for the closed‑by‑default framing, but it should not be mistaken for an implemented closed/open row semantics.

## Summary

- The **nominal‑structural flag** is a *type‑level* marker (`Named` vs `Anonymous`) that tells the compiler/plugin how to interpret a row; it does **not** affect the runtime representation.
- By defaulting ordinary declarations to `'Named` and requiring an explicit opt‑in for `'Anonymous`, Polytropos gains a **closed‑by‑default framing** for extensible records/variants. That framing is plausible and is a better fit than a pure nominal/structural label.
- The flag is **not** the same as a closed/open row discipline. Importing openness/closedness is the right conceptual axis, but it is not enough by itself: the augmented type system still needs the tail/variable, unification/inclusion, row polymorphism, and match/elimination pieces.
- The flag works together with the existing `RowType` phantom to distinguish products vs sums, giving a fine‑grained, zero‑overhead way to express closed‑named and structural‑open interpretations of the same underlying data layout — **within the limits of a library/plugin‑level discipline, not a full row‑kind/type‑system semantics**.

This mechanism is what enables the hybrid nominal‑structural design of Polytropos while maintaining backward compatibility **as a controlled closed‑default framing**, subject to the scope notes above.
